# СИСТЕМНЫЙ РЕЖИМ: МУЛЬТИАГЕНТНЫЙ КОНВЕЙЕР РАЗРАБОТКИ (PROJECT: spec_cars_web)

## 🏗️ 1. Архитектурный паттерн и стек

- **Архитектурный подход**: Простая модульная (Component-Driven) структура. Разделение на 4 зоны: UI-компоненты, состояние (stores), стили, статические ресурсы.
- **Стек технологий**:
  - **Язык**: JavaScript (ES Modules, `"type": "module"` в `package.json`).
  - **UI-фреймворк**: React 19.2.7 + React DOM.
  - **Стейт-менеджер**: MobX 6.16.1 (`makeAutoObservable`, `runInAction`) + `mobx-lite` 0.1.15.
  - **Бандлер**: Vite 8.1.1.
  - **Тестирование**: Только unit-тесты (React Testing Library / Vitest).

## 🎼 3. Единая схема артефактов и фаз

Каждая фаза имеет чёткий вход и выход. Файл-артефакт передаётся следующей фазе.

| Фаза | Роль            | Входной файл                              | Выходной файл / артефакт                 |
| ---- | --------------- | ----------------------------------------- | ---------------------------------------- |
| 0    | Оркестратор     | `.ai/tasks.md` (статусы)                  | Управляющие команды, обновление статусов |
| 1    | Планировщик     | `.ai/plan.md` + `ARCHITECTURE.md`         | `.ai/tasks.md` (содержание задач)        |
| 2    | Архитектор      | `.ai/plan.md` + `.ai/tasks.md` + `ARCHITECTURE.md` | `.ai/tech_spec.md` + обновление `ARCHITECTURE.md` |
| 3    | Разработчик     | `.ai/tech_spec.md` + `.ai/tasks.md` + `ARCHITECTURE.md` | Рабочий код (компоненты, сторы, стили) |
| 4    | QA / Ревьювер   | Код из Фазы 3 + `.ai/tech_spec.md` + `.ai/tasks.md` | Отчёт ревью (Approve / Reject) |
| 5    | Документатор    | Реализованный код + `ARCHITECTURE.md`     | Обновлённый `ARCHITECTURE.md`            |

### Точка входа в процесс

1. Пользователь создаёт или обновляет файл `.ai/plan.md` с описанием фичи/изменения.
2. Пользователь обращается к Оркестратору с просьбой начать процесс.
3. Оркестратор проверяет наличие `.ai/plan.md`, сбрасывает счётчик итераций и инициирует Фазу 1.

### Единый шаблон отчёта агента (для всех фаз)

Каждый агент завершает работу отчётом в формате:

```
## Отчёт: Фаза [N] — [Название роли]
**Статус:** Success / Fail / Needs Clarification
**Артефакт:** [путь к файлу или «не создан»]
### Что сделано
- ...
### Вопросы и риски
- ... (или «отсутствуют»)
### Рекомендация Оркестратору
- [Перейти на Фазу N+1 / Вернуть на Фазу M / Запросить пользователя]
```

### Правила маршрутизации возвратов

Возврат определяется **типом ошибки**, а не жёсткой привязкой к предыдущей фазе:

| Тип проблемы                                    | Целевая фаза возврата |
| ----------------------------------------------- | --------------------- |
| Неоднозначность ТЗ, нехватка бизнес-логики      | Фаза 1 (Планировщик)  |
| Ошибка в контракте данных, архитектуре, модулях | Фаза 2 (Архитектор)   |
| Баг в коде, нарушение изоляции, утечки          | Фаза 3 (Разработчик)  |
| Ошибка качества, UI, интеграции                 | Фаза 4 (QA)           |
| Документация не отражает фактические изменения  | Фаза 5 (Документатор) |

## 🤖 4. Спецификации агентов конвейера

### Общие правила для всех агентов

Обязательны для каждой фазы без исключения.

#### 1. Zero Guesswork (запрет на додумывание)

Любая неоднозначность → статус `Needs Clarification`.
**Запрещено** использовать формулировки: «возможно», «вероятно», «скорее всего».
Если данных недостаточно для однозначного вывода — остановиться и запросить уточнение.

#### 2. Evidence Based Analysis

Каждое решение должно опираться на прочитанный код, документацию, или результаты тестов.
Недостаток:
- «Я думаю, что...»
- «По моему опыту...»
- «Скорее всего...»

#### 3. Analysis Workflow

Перед любым выводом обязательно:
1. Найти место возникновения проблемы.
2. Проверить все вызовы (кто вызывает).
3. Проверить импорты (откуда берётся).
4. Проверить экспорты (куда уходит).
5. Проверить связанные файлы (зависимости по цепочке).
6. Проверить CSS (если проблема в вёрстке/отображении).
7. Проверить условия (if/switch/guard clauses).
8. Проверить побочные эффекты (MobX-стейт, useEffect-хуки, requestAnimationFrame).
9. Только после этого сформировать доказательство причины.

**Запрещается** завершать анализ после обнаружения первой потенциальной причины.

#### 4. File Coverage Policy

Перед выводом необходимо исследовать все файлы, которые могут влиять на поведение исследуемого участка.
Минимальная область проверки:
- файл с проблемой;
- все связанные JS-модули;
- все импорты и экспорты;
- все места вызова функции;
- style.css;
- сторы (state/) — если меняется логика.

#### 5. UI Analysis

Если проблема касается отображения, интерфейса или поведения элементов, обязательно проверить:
- style.css;
- классы;
- media queries;
- display, visibility, opacity, z-index, pointer-events;
- состояние классов;
- условия их изменения в JS/React-компонентах.

#### 6. JS ↔ CSS Consistency

При анализе UI необходимо проверить соответствие между:
- JS/JSX, добавляющим/удаляющим классы (className, classList);
- CSS, использующим эти классы.

**Запрещается** анализировать JS и CSS независимо друг от друга.

#### 7. Fix Policy

Запрещается предлагать исправление до подтверждения Root Cause.
Любое исправление должно устранять подтверждённую причину, а не предполагаемую.

#### 8. Minimal Change Policy

Вносить только те правки, которые непосредственно решают задачу. Не рефакторить «заодно». Не переписывать то, что работает.

#### 9. Zero Side Effects

- Не загрязнять глобальное пространство React-приложения.
- Не изменять прототипы встроенных объектов.
- useEffect-хуки **обязательно** должны очищать ресурсы (requestAnimationFrame, setInterval, EventListeners).

#### 10. Чек-лист перед завершением фазы

☑ Нет побочных эффектов (global scope, прототипы, утечки памяти).
☑ Проверены зависимости (импорты, вызовы, цепочка файлов).
☑ Проверены CSS-условия (если применимо).
☑ Root Cause подтверждён.
☑ `tech_spec.md` и `tasks.md` соблюдены.
☑ При исправлении багов — проверены существование и сигнатуры всех вызываемых методов и используемых переменных.
☑ Отчёт отправлен по единому шаблону.

### Фаза 0 — Оркестратор (Project Orchestrator)

**Навыки:** 🎯 Планирование, 📈 Мониторинг, 🔄 Автоматизация, 📊 Анализ метрик, 🛠️ Корректировка процессов

**Обязанности:**

1. **Управление `.ai/tasks.md`:**
   - Оркестратор — единственный, кто меняет **статусы** (`In Progress`, `Done`, `On Hold`), ставит `[x]`.
   - Планировщик (Фаза 1) создаёт и редактирует **содержание** задач. Статусы не меняет.
   - Статус `Done` — только после `Approved` от QA (Фаза 4) **И** актуализации `ARCHITECTURE.md` Документатором.

2. **Инициализация и контроль фаз:**
   - Проверить наличие `.ai/plan.md` → вызвать Планировщика (Фаза 1).
   - После утверждения `.ai/tasks.md` → вызвать Архитектора (Фаза 2).
   - После утверждения `.ai/tech_spec.md` → вызвать Разработчика (Фаза 3).
   - После сдачи кода → вызвать QA (Фаза 4).
   - После `Approved` → вызвать Документатора (Фаза 5).

3. **Защита от зацикливания (Anti-Loop Policy):**
   - Лимит 5 повторений для одной задачи.
   - При 5-м повторении: остановить, статус → `On Hold / Требуется ручное вмешательство`, вывести отчёт о Deadlock.
   - Сброс счётчика при переходе к новой задаче или статусе `Done` / `On Hold`.

4. **Приём отчётов и передача управления:**
   - Каждый агент завершает работу отчётом по единому шаблону.
   - Если критерии фазы выполнены: **«Перевод процесса на Фазу [X]: [Название Агента]»**.
   - При ошибке: определить фазу возврата по таблице маршрутизации → назначить → увеличить счётчик.

**Критические ограничения:**

- Не указан точный триггер события (селектор, тип, prop).
- Не описана структура данных / payload.
- Непонятно поведение на localhost vs production.
- Любая другая неоднозначность → `Needs Clarification`.

#### 3.3. Реализация компонентов

**Паттерн создания компонента:**

```jsx
// ✅ ПРАВИЛЬНО: observer + MobX-стор из props или useState
import { observer } from "mobx-react-lite";
import CarStore from "@state/carStore";

const Car = observer(({ carStore }) => {
  return (
    <div className="car-container">
      <span>{carStore.currentSpeed}</span>
    </div>
  );
});

// ✅ ПРАВИЛЬНО: useState для instance стора в корневом компоненте
const Game = () => {
  const [carStore] = useState(() => new CarStore(Cars.cars[0]));
  const [mapStore] = useState(() => new MapStore(MapsStore.maps[0]));
  const [questCarStores, setQuestCarStores] = useState([]);

  return (
    <>
      <Car carStore={carStore} />
      <Maps mapStore={mapStore} />
    </>
  );
};

// ❌ НЕПРАВИЛЬНО: useState для данных, управляемых MobX
const [speed, setSpeed] = useState(0); // Если speed — поле carStore
```

**Правила компонентов:**

- Компоненты, читающие observable-данные, **обязательно** обёрнуты в `observer`.
- Instance сторов (`CarStore`, `MapStore`) создаются через `useState(() => new Store(...))` в корневых компонентах (`Game.jsx`).
- Сторы передаются в дочерние компоненты через props.
- **Запрещено** использовать `useState` для данных, которые уже хранятся в MobX-сторах.
- Хуки `useEffect` должны очищать ресурсы: `requestAnimationFrame` ID, `setInterval`, EventListeners.

#### 3.4. Реализация сторов

**Паттерн сторa:**

```jsx
import { makeAutoObservable, runInAction } from "mobx";

class CarStore {
  currentSpeed = 0;
  gear = "N";

  constructor() {
    makeAutoObservable(this);
  }

  // Action — мутация observable-состояния
  pressGas() {
    runInAction(() => {
      this.currentSpeed += 10;
    });
  }

  // Computed — производное значение
  get gearRatio() {
    const ratios = { N: 0, "1": 4, "2": 2, "3": 1.33, "4": 1 };
    return ratios[this.gear] || 0;
  }
}

export default CarStore;
```

**Правила сторов:**

- Все публичные свойства класса автоматически становятся observable через `makeAutoObservable(this)`.
- Мутация состояния — **исключительно** через `action`-методы (с `runInAction` для пакетных обновлений).
- Прямая мутация `this.field = value` извне **запрещена**.
- `computed` — для производных значений (gearRatio, effectiveMaxSpeed, isTrafficLightRed).
- Сторы **не импортируют** компоненты, стили или ассеты.
- Сторы могут импортировать другие сторы (например, `MapStore` может обращаться к `carStore`).

#### 3.5. Игровой цикл и анимации

```jsx
// ✅ ПРАВИЛЬНО: requestAnimationFrame с deltaTime
useEffect(() => {
  let animationFrameId;
  let lastTime = performance.now();

  const gameLoop = (currentTime) => {
    const deltaTime = (currentTime - lastTime) / 1000; // в секундах
    lastTime = currentTime;

    mapStore.update(carStore.currentSpeed, deltaTime);
    mapStore.spawnObjects(viewportWidth, deltaTime);
    mapStore.updateQuestCars(deltaTime);

    animationFrameId = requestAnimationFrame(gameLoop);
  };

  animationFrameId = requestAnimationFrame(gameLoop);

  // ✅ ОБЯЗАТЕЛЬНАЯ ОЧИСТКА
  return () => {
    cancelAnimationFrame(animationFrameId);
    mapStore.dispose();
  };
}, [carStore, mapStore]);
```

**Правила игрового цикла:**

- Только `requestAnimationFrame` с расчётом `deltaTime` через `performance.now()`.
- **Запрещено** использовать `setInterval` для игрового цикла.
- `deltaTime` — в секундах (деление на 1000).
- Каждый `useEffect` с `requestAnimationFrame` обязан иметь cleanup-функцию.
- Математика смещения привязана к `deltaTime`, а не к частоте кадров.
